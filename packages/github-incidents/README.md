# Velvet GitHub incidents

`@velvet/github-incidents` owns Velvet-managed GitHub Issues for confirmed
outages and planned maintenance. It compares the current confirmed monitor
state with existing marked issues, applies only missing changes, and creates a
contract-valid public incidents document.

The package never deletes issues. Issues without one strict hidden Velvet
marker, including historical Upptime issues, are not treated as Velvet
incidents.

## Workflow requirements

Use the repository-provided `GITHUB_TOKEN`. No personal access token or other
user-managed GitHub API key is required.

Give the incident job only these permissions:

```yaml
permissions:
  contents: read
  issues: write
```

Every workflow that can update Velvet incidents must share one concurrency
group. Let the running job finish and keep the newest pending run:

```yaml
concurrency:
  group: velvet-status-data
  cancel-in-progress: false
```

This serial execution is part of duplicate prevention. The package also checks
hidden transition and action identifiers before every create, comment, reopen,
or close operation, so retried runs do not repeat completed work.

GitHub failures use stable `GitHubIncidentsError` codes and unique `errorId`
values. `githubIncidentErrorLog` returns only the operation, result, code,
error identifier, and HTTP status. Tokens, authorization headers, request
bodies, endpoint paths, and raw GitHub responses are not included.

## Planned maintenance form

Generate the form from the normalized Velvet services and write the returned
YAML to `.github/ISSUE_TEMPLATE/maintenance.yml` in the installed status
repository:

```ts
import { createMaintenanceIssueForm } from "@velvet/github-incidents";

const source = createMaintenanceIssueForm(
  configuration.services,
  configuration.incidents.maintenanceLabel,
);
```

The generated form shows friendly service and check names in a multi-select
field. The embedded identifiers let Velvet apply coverage to exactly the
selected whole service or individual check. Start and end values must be ISO
8601 timestamps with an explicit time zone, for example
`2026-08-01T22:00:00+02:00`.

GitHub converts submitted form values into ordinary Markdown. Velvet validates
that Markdown against the current normalized configuration and adds its own
hidden normalized marker. Invalid forms never suppress incidents and receive
one actionable validation comment per edited form version.

GitHub currently documents Issue Forms as a public-preview feature. The parser
therefore relies only on the documented Markdown headings and the stable target
tokens generated by Velvet.

Monitoring continues normally during maintenance. A covered confirmed outage
does not create an incident until the maintenance ends, but the measured
availability is never recalculated or corrected. The public history retains a
neutral maintenance event. Closing before the start cancels the event; closing
while active ends it early; an open issue is commented and closed automatically
after its planned end.

## Reconciliation

Call `reconcileGitHubIncidents` with the normalized services, current monitor
check states, configured labels, and one generated timestamp. The result
contains the public `IncidentsDocument`.

Confirmed outage transitions create one issue per service and check. Confirmed
recovery comments once and closes only open incidents for that target. If a
matching incident was manually closed while the monitor still confirms the
same outage, Velvet comments once and reopens it. If duplicate marked issues
already exist, Velvet keeps one primary issue and closes the extras without
deleting their history.

The monitor input is read-only. A GitHub API failure aborts issue processing
without changing monitor state; a later run compares the same durable state
with GitHub again and applies whatever is still missing.

## Tests

Run focused local checks with:

```sh
bun run --filter @velvet/github-incidents test
bun run --filter @velvet/github-incidents typecheck
bun run --filter @velvet/github-incidents build
```

The real GitHub integration test is opt-in and refuses repositories whose name
does not contain `integration`. It additionally requires an explicit isolation
flag:

```sh
VELVET_GITHUB_INTEGRATION_REPOSITORY=owner/velvet-integration-test \
VELVET_GITHUB_INTEGRATION_ISOLATED=true \
GITHUB_TOKEN=... \
bun test packages/github-incidents/test/github.integration.test.ts
```

The test creates unique labels and one uniquely marked issue. It closes only
issues carrying its own generated service identifier and never deletes an
issue. The token value must be supplied through the environment, never stored
in the repository or pasted into issue text.
